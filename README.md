# OPC 团建旅行社 Demo

一名人类老板，三个核心 Agent：项目经理、多角色策划、履约执行。客户决定体验取舍，老板处理超授权的经营和风险事项。此版供比赛演示，支付、供应商与自动活动事件为模拟。

当前演示暂停活动进度、现场异常和在线活动管理入口，保留方案审核、资源预订、付款、结算及历史订单。新团建订单由客户确认活动完成后结算，已有活动执行记录继续保存。下文涉及活动跟进的操作适用于重新启用该模块后的版本。

公司经营模块已从主入口拆出，市场调研、推广、优惠券和公司经营汇总的代码与数据保留在原模块。业务页面保留单笔订单费用、审批和收付款，历史订单继续按已核销的优惠结算。下文的经营演示步骤适用于单独启用经营模块后的版本。

命名约定：项目经理负责单个订单的需求、协调、交付与异常处理；公司层面的经营分析与财务职能使用“经营 Agent”称呼，属于后续讨论的独立职能角色。当前没有新增经营 Agent，财务金额仍由程序核算。内部角色字段 `manager` 保留，历史任务日志保留原始称呼；旧档案读取时识别为同一项目经理岗位。

## React 双端演示

用户端和老板端通过同一个本地 Python 服务读取案件、模拟预订和账本。用户端的未提交草稿保存在当前浏览器。提交后的「我的活动」使用浏览器会话读取后端记录。老板端登录使用本地演示口令。

在项目根目录安装 Python 依赖，然后构建两个前端。

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
npm.cmd --prefix frontend/customer ci
npm.cmd --prefix frontend/customer run build
npm.cmd --prefix frontend/boss ci
npm.cmd --prefix frontend/boss run build
```

已经安装前端依赖时，也可以直接用 Node 运行各自目录的 `node_modules/vite/bin/vite.js build`。策划使用项目已有的 `LLM_API_KEY`、`LLM_BASE_URL` 和 `LLM_MODEL` 设置。

```powershell
$env:MIYOU_OWNER_PASSWORD = Read-Host '设置本次演示的老板口令'
.\.venv\Scripts\python.exe -m uvicorn src.web_api:app --host 127.0.0.1 --port 8000
```

- 用户端打开 [咪游社](http://127.0.0.1:8000/)。创建北京 15 人、1 天、人均 700 元的活动，日期选未来一天，确认后跟随 AI 工作台的步骤。
- 方案确认后查询午餐报价，选择一条可用报价，确认合同条件并支付模拟预付款。
- 老板端打开 [老板工作台](http://127.0.0.1:8000/boss/)，输入本次口令。从「待审批」进入同一案件，授权模拟供方定金，再提交模拟预订。
- 回用户端查看回执、确认交付并支付模拟尾款。回老板端授权结清，最后查看「经营复盘」。

两个入口设计为同一台电脑本地演示。测试使用临时案件与账本，并以固定模型响应跑通流程。

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -p test_web_order.py -v
```

## 历史订单管理与可检索经验

老板切换工作区到“历史订单管理”，可按订单类型、履约阶段、编号、城市和标题筛选，查看并下载完整原始档案、查看关联酒店餐饮合同，或恢复到客户页面/老板工作台的原有步骤。此工作区不依赖 MiMo 密钥，不会重新执行策划、收款或预订。

“方案已确认”与“已履约并结算”分别展示。策划案和关联预订合同会各占一行，不能把行数作为客户数、订单收入或利润。供应商和付款保持模拟属性。

完整案件继续存放在 `data/current_case.json` 的案件集合中；供应商合同与流水继续存放在 `data/company_simulation.sqlite3`。新模块不会替换、清空或按时间裁剪这些原始档案。另建 `data/current_case_history.sqlite3` 作为可重建的片段/向量索引，按需求、方案、决策、执行、反馈、经验、财务的业务意义拆分，每个片段保留订单编号、方案版本和原字段路径。老板可以停用某个片段，完整原文仍然保留；重新同步索引保留停用设置。删除原案件后，其片段也会从后续检索移除。

新案件策划、执行检查和项目经理整合时，共享最多4条历史参考，每个来源最多2条。不引入新的 MiMo 调用；相同需求复用检索结果，历史档案或停用设置变化后刷新。草案可在老板端查询，但不自动注入其他订单。财务片段供老板查看，不自动注入策划提示词。历史报价、房量、档期和付款状态均不得直接沿用。原有“反馈与改进”经验机制保留；后台展示“已提供给哪些角色”，不把提供资料冒称为已经采纳或实际改进。

默认使用本地字段和中文关键词检索，可直接运行。关键词检索不能理解所有近义表达。Redis 和本地向量模型分别可选，均不要求更换 MiMo：

```dotenv
# 留空时使用本地索引；配置时需 Redis 实例具备 Search 功能。
HISTORY_REDIS_URL=
# 仅填写已下载到本机的 SentenceTransformer 模型目录；不会自动联网下载。
HISTORY_EMBEDDING_MODEL_PATH=
```

使用 Redis 前执行 `python -m pip install -r requirements.txt`，再在 `.env` 设置 `HISTORY_REDIS_URL`（例如本机实例 `redis://127.0.0.1:6379/0`）。历史搜索时自动建立 `opc_history_*` 前缀的独立 Search 索引、同步启用片段并返回候选；不会清空 Redis 的其他键，不给经验设置会话过期时间。连接失败、没有 Search 或客户端库未安装时，页面明确提示并回退本地检索。Redis 是原档案之外的检索副本，不是唯一数据来源。

可选语义检索：安装 `python -m pip install -r requirements-memory.txt`，提前下载例如 `BAAI/bge-small-zh-v1.5` 的完整模型目录，设置 `HISTORY_EMBEDDING_MODEL_PATH` 后重启。模型在本地 CPU 加载，首次向量化需等待，后续复用文档向量；更换模型文件后重新计算。没有 Redis 时也能在本地比较向量；有 Redis Search 时同时建立向量索引。加载失败会明确回退关键词检索。目前未加入独立 Rerank 模型。索引中是已有业务记录的程序提取，不伪造历史订单或新增模型总结。

检索功能不等于生产鉴权：目前仍是演示身份切换。老板档案页面只在老板身份展示；正式上线前需接入账号与租户隔离。

## 重新进入、刷新与历史案件

客户新开页面或离开后重新进入时，从新需求开始，不自动展示上一单。普通刷新保持同一次访问，恢复该次已保存的案件、角色和工作区。浏览器以sessionStorage和导航类型区分新进入与刷新；不会因为等待一段固定时间就擅自清空正在办理的订单。

已提交内容和每个业务检查点持续保存，不依赖关闭页面时发送“退出”消息。老板端“历史案件与未完成进度”可切换任何已保存案件，点击“在客户页面继续此案件”恢复对应的需求确认、提案、草案、审批、资源或活动步骤。客户也可点击“保存进度并开始新需求”，旧案仍留档。未提交的表单输入不属于业务检查点，不承诺跨关闭恢复。

酒店餐饮预订同样区分访问：客户新访问默认新建需求，老板可查看全部模拟订单并点击“在客户页面继续此预订”。同次刷新恢复该预订；已付款、已核销优惠与供应商回执由原交易记录恢复，不重复执行。运营模块的数据属于公司记录，不随新客户访问清空。

`data/current_case.json`现使用多案件容器，按案件保存完整快照和各自版本；旧单案件文件首次写入时兼容迁移，不丢弃原记录。后台继续保存旧案件不会覆盖或切走新客户正在处理的另一案件。删除只影响指定案件，旧页面不能重新保存已删除案件。原始上传文件未另存时仍需重新上传，已提取并保存的文档文本与业务记录继续保留。

浏览器访问检测使用Streamlit组件，最低版本已更新为1.66。当前环境已满足；其他设备同步代码后按`requirements.txt`更新依赖，再启动服务。

## 酒店餐饮与公司运营工作区

左侧保留“客户 / 公司老板”身份切换，新增三个工作区：“团建策划与交付”“酒店餐饮模拟预订”“公司运营模块”。全部供方、库存、联系、付款、推广及优惠核销均为模拟，无真实交易，不会发送邮件、短信或真实预订。

酒店餐饮属于核心业务，由履约执行Agent选择联系人并调用模拟询价工具。支持直接创建酒店餐饮需求，也可关联尚无旧版资源订单的当前案件。原日期2026-11-06至08作为历史演示保留；预置男100、女50，共75间双床房、两晚。客户明确目的地和实际餐次；“200人天”不自动解释为预算，表单允许确认元/人/天或暂不确定。酒店逐晚核验房量，餐厅逐餐核验餐位；菜单、报价、取消条件和回执独立保存。

可立即载入固定模拟供应商（零模型调用），也可按按钮调用一次模型生成并保存场景。后续库存、报价有效期、资金和预订结果由程序维护。执行Agent一次输出结构化联系动作，程序检查供应商编号和餐次，再生成模拟回复；未知供方、容量不足、过期或库存已变的报价不能预订。提供报价过期和第二晚房量减少事件，方便演示重新核实。

客户选择一家连续房量满足的酒店及覆盖全部餐次的餐饮报价，逐项确认服务变化。酒店报价仅包含客房，不包含活动场地、篝火或烟花，相关能力与合同范围分别展示；客户不接受排除项就不确认合同。合同行为绑定报价签名。确认后可选一张服务费优惠，模拟支付60%客户预付款；老板显式授权资源费用30%的供方定金，执行工具才可提交预订、扣减库存并取得SIM回执。随后客户确认交付并模拟支付尾款，老板结清供方后完成本单。重复提交不重复记账、占用库存或核销优惠。

关联原团建案件时，资源未确认不能启动活动演示。若预订条件取消原行程中的火源活动，先显示原安排和改为自愿休息的执行建议，由客户确认后才启动；原策划版本保留。其他替代活动需另行确认。首版不支持拆分酒店，也不自动处理供方付款后的改期、取消及退款；需要保留记录并人工处理。

公司运营作为可调用模块，不新增常驻Agent或每单强制调用。市场调研提供固定模拟竞品报告和一次按需模型报告，不声称联网搜索或真实市场验证；获客活动从草案、老板批准本地启用到模拟咨询登记，保留来源活动；优惠政策明确服务费范围、门槛、有效期、客群、额度和不叠加规则，可停用。客户领取后在本单付款时原子核销；重复核销、跨客户使用、过期、超发及服务收入不足均会拒绝。优惠后至少保留500元本单服务收入是演示参数，非真实经营标准。

新工作区使用标准库SQLite存储于`data/company_simulation.sqlite3`，并发操作在同一事务中校验库存、优惠与资金事件。公司模拟现金仅初始化一次为46000元，支出后保留15000元；该总账覆盖新酒店餐饮订单及模拟推广支出，不合并旧固定演示账。统计展示客户来源、成交转化、已完成服务收入和模拟现金；预付款不列已完成收入，服务收入尚未扣除推广等公司费用。没有数据时不编造转化率。

演示建议：老板在公司运营模块生成模拟报告、创建并启用活动及优惠政策；客户登记咨询、领券；在酒店餐饮工作区确认150人历史需求，载入或生成场景、让执行Agent联系；选择酒店B或C和可接待150人的餐饮报价，确认范围、用券、付模拟预付款；老板授权定金，执行工具取得回执；客户确认交付、支付尾款，老板结清，再回到经营记录查看转化、核销和现金。

MiMo可使用 `LLM_BASE_URL=https://api.xiaomimimo.com/v1`、`LLM_MODEL=mimo-v2.6-pro`。正式小米域名下默认发送 `thinking.type=disabled`，避免简单业务任务额外等待；其他接口不发送这个参数。MiMo底层请求时限75秒、单次模型总时限90秒，其他接口分别为45秒和60秒；关闭SDK隐式重试，由页面控制明确重试。MiMo资源预订和现场协调每步限时30秒；其他接口沿用原时限。失败仍明确提示或标记规则降级，不把超时当成功。

## 客户上传文档

客户可在需求表单上传 Word（`.docx`）、PDF 或参考图片，一次最多3个附件。Word单个不超过12 MB，按顺序提取正文段落和表格，最多读取24000个字符，再由项目经理整理偏好、硬性要求和待确认事项；客户在需求确认页检查后开始策划。读取Word不新增模型调用环节，也不需要安装Word或额外解析依赖。

旧版`.doc`需先在Word中另存为`.docx`。内嵌图片不作OCR识别，请单独上传图片；页眉页脚、批注、文本框等不属于本次读取范围。损坏、加密、过大的文档会显示附件分析失败或具体提示；空文档和截断内容也会提示，不编造识别结果。附件内容不能修改公司权限或跳过审批。

## 已有活动方案审核

客户首页明确提供“自己选择并填写”和“直接上传Word/PDF”两条入口。上传后先从全文提取已有信息，客户再选择“按已有方案接入在线活动管理”或“根据文档需求定制团建旅行”。只补缺失的必要信息，每轮最多两个字段，填写数字或日期无需再调用模型；已识别的内容只显示确认卡，可选择修改。旅行需要城市、日期、人数；活动管理需要日期、场地、参与总人数，不强制填写预算、旅行风格或猜测人数。原文只有推荐名额时不能推算总人数。

文档读取和需求提取一次模型调用；信息确认后，项目经理审核原文事实、流程与规则，策划Agent提出筹备、现场、收尾的执行清单，再调用两次。原文引用须匹配才能列入事实；程序可核对明确列出的奖项金额与行政支出总额。差额仅提示核实用途，不擅自认定错误或修改预算。所有新增岗位、时间分配和规则是建议，未通知、派发或批准。

客户可补充审核问题并重新审核，历史完整结果最多保留3版，可下载Markdown清单。确认收到清单只完成审核交付；随后客户核对执行信息并选择纳入管理的环节，显式创建在线管理订单。此模式不进入旅行提案、预订、收款或旅行方案反馈复用流程；已有订单的原文和执行快照不会因重新审核而被覆盖。

活动看板按组织者操作推进，不会自动注入旅行天气提醒。可上报投影/音响故障、环节延迟、关键人员缺席、成员休息或其他具体情况，也可点击明确标记的“演示一次投影故障”。履约核查、必要时策划调整、经理审核沿用三个核心Agent，每步最多20秒，失败明确转为规则建议并暂停等人工核查。调整只允许涉及当前与未来环节，额外或未知费用交老板；老板批准后仍交组织者确认，所有活动事件均需组织者确认才能恢复。记录、原始顺序和调整后顺序保存，演示事件与现场上报分开标明；不代表自动维修、通知或支付。

## 三个核心 Agent

| Agent | 职责 | 调用位置 |
| --- | --- | --- |
| 项目经理 | 需求与附件理解、投诉核查、组合草案、运营和风险检查、资源决策 | `workflow.py`、`procurement.py`、`journey.py` |
| 多角色策划 | 宋野、沈知行、夏橙三个人设；三风格精简提案、行程返工和局部调整 | 同上 |
| 履约执行 | 策划可行性检查、修改后必要复核、选择资源、判断现场变化影响 | `compact_planning.py`、`workflow.py`、`procurement.py`、`journey.py` |

`build_agent_team()` 只创建三个 Agent 实例。三个策划人设共用一个 Agent，不是三个独立 Agent。运营与风险是经理一次调用的两项检查，另由程序执行结构和权限规则；不宣称独立双审。

流程由程序状态机驱动，模型在各任务中返回结构化判断；本版不是不受约束的自主调度系统。模型不能直接改账、批准自身建议、编造供方回执。

## 演示主线

1. 客户选择城市、日期、人数、预算、偏好和硬性条件，确认需求卡片。结构化表单不重复调用模型提取。
2. 策划一次生成三份精简提案，客户选风格，可质疑或投诉；经理核查有证据的投诉，偏好不算失职。
3. 新案件由履约一次检查客户选中的方向，写明具体依据、解除条件和待落实资源；经理一次整合草案并同步完成运营与风险检查，记录如何处理分歧。客户确认未修改的普通草案后，程序复用精确匹配的检查并继续运行硬性规则。明确阻塞、客户微调、需求或版本变化时增加履约最终复核；客户和老板权限继续生效。
4. 客户评价最终方案，保留版本、贡献与反馈依据；拒绝则进入返工。
5. 客户确认模拟合同与住宿条件，模拟支付60%预付款。供应商工具返回场地、车辆和住宿回执。
6. 住宿不足时：履约选择候选 → 策划处理交通对行程的影响 → 程序即时计算财务 → 经理选择最终建议。财务不调用模型，内部金额与客户公开提示分开。候选不存在、房量不足或越步骤改行程会被程序拒绝。
7. 超经营授权交老板；住宿、交通或执行行程变化交客户。老板批准不能代替客户同意。完成后生成 SIM 确认编号。
8. 老板可点击“授权模拟供应商支出”。活动执行沿用已确认执行行程，保留原策划版本。
9. 自动模拟降雨、成员休息需求，或由现场负责人上报延迟、休息、下雨。履约诊断 → 必要时策划局部调整 → 经理核查。需要变化时停下来等客户确认，重大事项交老板。
10. 活动完成后，客户确认并模拟支付尾款，系统结算本单、记录履约完成。重复操作不会重复记账或重复累计完成记录。

建议用例：南京、30人、1天或2天1晚、预算9000元。下模拟订单时选择1晚住宿可触发酒店不足。可保留同级远端酒店并由老板承担利润取舍，或由老板选择近端酒店后请客户确认等级变化。

## 财务与反馈改进

- 模拟供方资源报价按合同价固定比例生成，不代表市场真实报价。
- 报价减资源成本为服务空间；预计利润另扣合同价1%的 AI运营成本和5%的风险预留。预留未实际使用时，不在完单账中当作支出。
- 每单以46000元期初现金演示，不是跨订单总账；模拟付款后必须保留15000元生存准备金。展示预付款、支出、待付款、尾款、现金、预收义务和收入利润。
- 收预付款时不确认收入利润；活动结束并结算后才显示本单结果。支付与尾款必须由相应页面的明确操作触发。
- “协作与分歧”展示提案、对应行程和采纳依据。“反馈与改进”保留方案版本、客户原话和可复用经验。新订单的改进来自历史反馈，旧档案可继续读取。
- 满意结论保存本版完整方案作为模板候选，具体好评与负面意见分别保存为经验和检查项。客户拒绝时可填写不满意的地方，并在原订单发起新版本。结清后可单独评价实际体验。新增经验时显示“已学习情景”，老板端“反馈与改进”保留时间、来源订单、版本和阶段。
- 记录包含来源案件、版本、阶段、原方案、适用条件。方案好评不等于成功履约。相似条件的下一单选取最多2条经验、3条检查项；城市、风格、人群、时长及已有硬条件/特殊需求采用保守文本匹配，不声称语义检索。人数和预算作为来源背景，必须按本单重新核算；条件不足不跨单自动复用。
- 历史参考随既有业务调用交给策划、履约和经理，不新增模型调用。经理在最终方案说明采用、调整或不适用，并引用真实记录ID及有效行程下标。后台区分“提供了参考”和“经理说明采用”，不把模型说明当成已执行成功。老板可以停用不合适的记录；新投诉检查项按相似场景复用，不自动变成全公司禁令。
- 演示：第一单选择“满意”并勾选具体原因，或填写“分组很好，不勉强任何人”；老板查看生成记录。新建相同城市、人群、风格、时长及硬条件的订单，在“反馈与改进”查看参考来源及最终处理说明。停用记录后，后续调用不再提供。原有公司制度与付款审批继续生效。

## 等待与异常

### 已校验结果复用与阶段契约

- 策划提案、履约可行性检查、方案整合和方案复核可在同一案件内复用已通过结构与边界校验的结果。缓存记录随案件保存，最多24项、有效期15分钟；失败、格式错误、无行程的方案和损坏记录不命中。缓存不代表业务语义绝对正确，后续程序规则、履约复核及客户/老板审批仍照常执行。
- 缓存键包含角色、实际提示词、角色规则、输出契约、模型与接口、公司政策、案件/阶段/方案版本、需求和约束等；输入或配置变化后重新调用。原有快速检查缓存也增加时间、模型/规则和历史参考的失效条件。旧案件缺少缓存元数据时重新核查，不补造成功记录。
- 库存、报价、供应商联系、现场事件、支付及审批操作不进入这类结果缓存。任务记录以`validated_cache`标记复用，耗时不冒称模型推理时间；“相似历史经验”不等同于“相同输入结果”，不能据此跳过检查。
- 每次请求按“稳定角色规则 → 稳定阶段要求与Schema → 动态订单资料”组织。Schema只去除显示用标题及默认值描述，保留字段、类型、必填项和校验规则；运行时继续使用Pydantic验证。未添加其他厂商专有缓存参数，实际服务端命中和延迟需由真实接口统计验证。
- 项目经理按阶段返回较小结构：`ProjectPlan`只生成方案与一份依据；`ProjectDraft`在方案之外返回统一问题列表；`ProjectReview`只返回问题及完成条件，不重新生成行程。问题保留运营/风险类别、证据、解除条件、决策人和阻塞性。程序推导检查结论，并转换回兼容原页面与存储的`CouncilDecision`、`ManagedPlan`和`ManagerReview`；有效旧格式也可直接解析，不增加格式修复调用。
- 后台显示本轮交付完成条件及检查证据。它们不等同于资源已落实、客户已同意或公司已批准。

代码分工：`src/result_cache.py`负责有范围和期限的复用，`src/stage_schemas.py`负责阶段结构及兼容转换，`src/agents.py`负责稳定前缀与模型请求。

客户等待区只展示最近四条公开业务摘要和流程状态，阶段完成后交给下个角色；预订和活动响应同样显示实时任务交接。状态提示明确区别于模型业务意见，不为制造对话增加模型调用。老板端实时查看后台任务，完整审计和失败原因另行保留。

同一 Streamlit 服务进程的多个浏览器会话，通过 `runtime.py` 按案件、订单、步骤、事件和重试次数共用进行中任务，并只提交一次结果。业务真相仍由 `TravelCase` 的版本化文件保存；不是跨进程或重启后可继续运行的持久任务队列。服务重启后可从保存步骤继续，旧任务结果不能覆盖新版。

后台意外异常保留原步骤，页面提供明确重试，避免红屏与自动重复请求。低风险非阻塞提醒保留在待核实事项中，不再反复返工；高风险或明确需人工决定的问题仍阻塞。空行程不能发布或收预付款。

活动响应提供结构化新增费用；正金额、未知金额或文本中的明确新增金额，均由程序要求老板确认。费用尚未核对不能结算；老板可在活动异常区域核对金额并记录模拟支出，0表示确认无新增支出。该支出进入现金与利润计算，重复操作不重复记账。

新建普通表单案件，没有附件、投诉、修改、返工或阻塞时，策划主线为三次调用：策划精简提案、履约检查、经理整合并检查。初稿不生成完整时间表，空的可选字段可省略；完整行程仅在整合时生成。检查缓存绑定需求、风格反馈、有效约束、文档、提案、方案和版本；输入变化不得复用。履约要求客户或老板决定的事项不能被经理删除；经理声称修复阻塞时仍增加履约复核。高风险、投诉、修改和返工可能超过三次，不为减少调用跳过权限。

资源协调保留四个业务步骤，其中财务为即时程序计算，因此模型调用从四次降为三次。任务记录明确区分程序、模型和规则降级。MiMo资源任务和活动协调每步最多30秒；其他接口资源任务12秒、旅行协调8秒、文档活动协调20秒。现场无需重设计时跳过策划。失败明确标记；活动检查失败会交老板，不自动应用修改。

等待时间取决于模型与网络，减少调用次数不等于已验证提速。未进行真实接口性能承诺。

旧案件使用默认字段迁移，原始需求、学习记录和支付记录保留。旧策划案件继续原有互评与审核流程。新建案件使用 compact_v1 流程。
